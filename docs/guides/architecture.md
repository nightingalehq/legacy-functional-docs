# Architecture overview

Audience: engineers who need the technical shape of the system before
extending it, integrating it, or assessing it. For a plain-language
introduction, see [getting-started.md](getting-started.md). For the design
rationale (why it's built this way), see `SKILL.md` and
[`docs/plans/legacy-functional-docs-plan.md`](../plans/legacy-functional-docs-plan.md).

## The core idea

Documentation generated by an LLM reading raw source directly is fluent and
sometimes wrong in ways nobody can spot by reading it. So the pipeline
separates **fact extraction** (deterministic, auditable, no model involved)
from **narrative writing** (the only stage where judgement enters, and its
inputs are constrained so there's less room for it to drift):

```
source files ──▶ [0 Ingest] ──▶ [1 Extract] ──▶ [2 Derive] ──▶ SQLite fact store
                                                                      │
                                                                      ▼
                                                              [brief generation]
                                                           (+ redaction, if enabled)
                                                                      │
                                                                      ▼
                                                          [3 Narrate] (human or
                                                           `mfdoc batch` + Claude API)
                                                                      │
                                                                      ▼
                                                             markdown documents
                                                                      │
                                                                      ▼
                                                              [4 Validate] ──▶ pass/fail
```

Stages 0–2 and 4 are plain Python with no network access and no
model calls. Stage 3 is the only stage that can call out to Anthropic's API,
and only when you explicitly choose `mfdoc batch` over the interactive
Claude Code path.

## Stage by stage

### 0 — Ingest (`mfdoc ingest`, `normalise.py`)

Reads whatever files `project.yml` points at, per source set:

- Detects or applies a forced text encoding (mainframe exports are often
  EBCDIC code pages like `cp037`/`cp500`).
- Strips sequence columns (mainframe listings often carry line numbers in
  fixed columns that aren't part of the source).
- Splits one physical file into one or more **members** — a SYSOBJH unload
  or a PDS listing routinely holds many logical programs concatenated
  together. Splitting uses per-dialect default patterns, overridable via
  `options.splitters` in config.
- Detects (or takes a pinned) **dialect** per source set: `natural`,
  `mantis`, `adabas_fdt`, `ddm`, `supra_dir`, `sql_ddl`, `cobol_copybook`,
  `jcl`, `cics_csd`.

Ingest is incremental: a file whose `sha256` matches the `source_file` row
from the last run is skipped outright, and everything it owns (members,
derived facts) is left exactly as it was. A changed file's members are
purged and re-extracted (`db.purge_member_facts`, keeping the member's `id`
stable if its identity — name/library/dialect — is unchanged) rather than
appended alongside the stale rows; a member a changed file no longer
produces at all is purged outright (`db.purge_member`). This is what makes
running `mfdoc ingest` a second time against a large, mostly-unchanged
codebase cheap, and it's what `mfdoc derive` also has to be idempotent
against — see its own note below.

Every ingested line is recorded verbatim in `source_line`, keyed by member
and a 1-based `line_no` — this is the addressing scheme every citation in
every generated document ultimately points back to. Ambiguous or
unrecognised dialects become `gap` rows rather than silent best-guesses.

### 1 — Extract (`src/mfdoc/dialects/*.py`)

One module per dialect, routed by `DIALECT_ROUTER` in `cli.py`:

| Module | Dialect(s) | Notes |
|---|---|---|
| `natural.py` | Natural | Reference implementation; most mature |
| `mantis.py` | Mantis | Calibration expected on a new codebase |
| `adabas.py` | `ddm`, `adabas_fdt` | Two listing formats for the same underlying entity |
| `supra.py` | `supra_dir` | Calibration expected |
| `environment.py` | `sql_ddl`, `cobol_copybook`, `jcl`, `cics_csd` | Surrounding infrastructure, not application logic |

Each scanner is a heuristic line-and-clause matcher (regex-driven), not a
parser built on a formal grammar — mainframe 4GLs mostly don't have public,
complete grammars to build one from. They're built to **flag what they
can't parse** as an `unparsed_line` gap rather than to silently skip or
guess it. This is the load-bearing design choice for the whole project's
trust model: recognition rate is a measured, reportable number, not an
assumption.

Extraction populates (see `db.py` for the full schema):

- `member`, `source_line` — provenance
- `entity`, `entity_field`, `entity_link` — data definitions and their
  relationships (Adabas coupling, Supra linkpaths, foreign keys)
- `variable`, `data_access` (the CRUD-matrix backbone), `call_edge`,
  `transaction_marker`, `interaction`, `rule_candidate`, `message_ref`
- `job_step`, `job_dd`, `cics_resource` — batch/online orchestration
- `gap` — anything not resolved, with a `severity` and free-text `detail`

### 2 — Derive (`mfdoc derive`, `graph.py`)

Joins raw facts into structures no single scanner pass can produce alone:

- `reconcile_adabas_files` — merges DDM and FDT records of the same
  physical file into one `entity` row (a common source of phantom
  duplicate entities if skipped).
- `resolve` — resolves `call_edge.callee_name` against known members;
  unresolved calls become `missing_source` or `dynamic_target` gaps
  depending on whether the target was a literal or a variable.
- `crud_matrix`, `orphans`, `transaction_scopes`, `call_closure` — the
  derived views that feed briefs and, eventually, process-flow documents.
- `coverage` — the headline numbers (`line_recognition_rate`,
  `call_resolution_rate`, `entity_definition_rate`, gap counts by
  severity) that `mfdoc gate` checks against `options.quality_gates`.

Everything here is still deterministic and still free of model calls.
`run_all` is idempotent — it purges its own previously-derived gap rows
(`DERIVED_GAP_KINDS`: `orphan_module`, `unresolved_call`, `no_ddl_for_entity`,
`ambiguous_adabas_file`, `sme_question`) before re-deriving, so running
`mfdoc derive` twice against an unchanged index — a normal thing to do now
that `mfdoc ingest` can legitimately no-op — reproduces the same `coverage()`
output rather than doubling every gap.

### Quality gate (`mfdoc gate`, `GATES` in `cli.py`)

A thin, explicit check: for each configured gate, compare a `coverage()`
value against a threshold (min or max) and report pass/fail plus what a
failure blocks. Exists so a weak index is a **hard stop enforced by a
process**, not an instruction a model or a person under deadline can choose
to skip.

### Calibration (`mfdoc calibrate`, `DIALECT_CALIBRATION_HINTS` in `cli.py`)

Groups `unparsed_line` gaps for one dialect by leading keyword, ranked by
frequency, and points at the specific file and constant most likely to need
a new pattern. This is expected, routine work for Mantis and Supra on a new
codebase (see `reference/mantis-supra.md`), not a fallback for when
something's broken.

### Brief generation (`mfdoc brief`, `brief.py`)

Produces the plain-text input to the narrative stage: `module_brief`
(one program), `entity_brief` (one data store), `system_brief` (the whole
system), plus `json_index` for downstream tooling (`mfdoc export`). A brief
contains only facts already in the store, each already carrying its
citation — the narrative stage's job is reduced to "write from what's
already true and cited," not "find and verify facts while also writing
prose."

**Redaction** (`redact.py`) runs here, on the brief text, before anything
is written to a file or sent anywhere — not later, at document-render time,
when sensitive values would already have reached a prompt. See
[security-and-compliance.md](security-and-compliance.md) for what this does
and does not cover.

### 3 — Narrate (two paths, by design — see the plan doc's "Option C")

High-volume, formulaic documents (one per program) and low-volume,
judgement-heavy documents are deliberately routed differently:

- **`mfdoc batch` (`batch.py`)** — for module docs only. For each batchable
  member (`natural`/`mantis`, `object_type` in
  `program`/`subprogram`/`subroutine`/`copycode`): generate brief → call a
  `ModelCaller` with `reference/writing-rules.md` and `templates/module.md`
  → write the doc → validate → retry once with the failure appended to the
  prompt. Resumable via a state file keyed on brief content, so an
  interrupted run over thousands of members picks up where it left off.
  `ModelCaller` is a plain callable protocol; `AnthropicCaller`
  (`anthropic_caller.py`) is the real implementation, isolated in its own
  module so the `anthropic` package stays an optional dependency. A
  `fake-echo` caller exists for CI/dry-run smoke tests with no network call.
- **Interactive, via Claude Code (`SKILL.md`)** — for system overview, data
  entity docs, process flows and the gap register, where grouping and
  narrative structure benefit from a human (or a chat session) holding the
  whole system in mind, which batching would not support well.

### 4 — Validate (`mfdoc validate`, `validate.py`)

Parses YAML front matter and body of each generated document and checks:

- Every `[[MEMBER:LINE]]` or `[[MEMBER:LINE-LINE]]` citation resolves to a
  real member and a real line range in the fact store.
- Required front-matter keys are present and `review_status` is a valid
  value.
- Every assertive sentence (`_uncited_assertions`) carries either a citation
  or an explicit hedge (`inferred`, `unresolved`, etc.) — the mechanical
  enforcement of "never assert behaviour that cannot be traced to a
  specific source line."

This is the only stage that reads generated documents back in; everything
upstream only ever writes forward.

## Data store

Everything lives in one SQLite file, `.mfdoc/index.db` by default
(`options.index_db` in config). Full schema in `db.py`; the tables above
map directly to it. It is:

- **Rebuildable from source at any time** — nothing is hand-edited into it,
  so it's gitignored, and losing it costs a re-run, not data.
- **The audit trail** — `ingest_run` records tool version and the config
  used; `source_file.sha256` records exactly what was read. `project.yml`,
  by contrast, *is* committed, so a run is reproducible and its provenance
  is a diffable, versioned artefact.
- **A security-relevant artefact in its own right** — it contains every
  source line ingested, unredacted (redaction is applied only when briefs
  are generated from it). See
  [security-and-compliance.md](security-and-compliance.md).

## Where a model can and can't reach

The only code paths that make a network call are `mfdoc batch` and
`anthropic_caller.py`. Everything else — `ingest`, `derive`, `coverage`,
`gate`, `calibrate`, `brief`, `validate`, `export` — is local Python with no
egress, which is why the README states "no network access, nothing leaves
the machine" as the default posture with `mfdoc batch` as the one named
exception.

The interactive path (writing docs from a brief inside a Claude Code chat
session, per `SKILL.md`) also sends brief content to a model, just via
whatever surface is running Claude Code rather than via this repo's own
network call — worth remembering when reasoning about data flow, since it's
easy to read "no network access" as covering that path too.
